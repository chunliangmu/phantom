# AGENTS.md

Phantom: 3D SPH/MHD astrophysics code, written in Fortran 90 (`gfortran`/`ifort`/`ifx`/`aocc`). The whole codebase is Fortran; Python exists only for analysis (the local `sarracen/` clone, `scripts/pyphantom` which is Python 2 only, docs build).

## Build

- The root `Makefile` is a thin wrapper that delegates everything to `build/Makefile` (`cd build; make ...`). Run make from the repo root.
- Both `SYSTEM` and `SETUP` are **required** on the command line, e.g.:
  `make SYSTEM=gfortran SETUP=star`
  - `SYSTEM` selects a compiler block in `build/Makefile_systems`; this machine always uses `gfortran` (flags in `build/Makefile_defaults_gfortran`).
  - `SETUP` selects a compile-time configuration block in `build/Makefile_setups` (e.g. `star`, `disc`, `sedov`, `test`, `testgrav`, ...). Unknown SETUP = hard error with a hint. Day-to-day work uses `SETUP=star` (sometimes `dustystar` or `radstar`) for binary-star simulations.
- Default target `make` builds the main `phantom` binary. Other binaries, each its own target (all need SETUP): `phantomsetup`, `phantomtest`, `phantommoddump` (alias `moddump`), `phantomanalysis` (alias `analysis`), `phantomevcompare`, ...
- Changing SETUP/SYSTEM/FFLAGS/FPPFLAGS automatically triggers `make clean` (tracked via `build/.make_last*` files). Full rebuilds on config change are normal, not a bug.
- Binaries land in `bin/` (gitignored via `bin/.gitignore` containing `*`); `build/*.o` and `*.mod` are gitignored, as is `build/phantom-version.h` (generated from version numbers at the top of `build/Makefile`).
- `OPENMP=yes` (OpenMP) and `DOUBLEPRECISION=yes` are defaults; `DEBUG=yes` adds debug flags. Extra switches via env var, e.g. `MPI=yes` (or `MPI=openmpi`).

### Config system (important)

- `.F90` sources are C-preprocessed (cpp); `.f90` are not. Preprocessor macros (`-DGRAVITY`, `-DMHD`, ...) come from the SETUP block in `build/Makefile_setups` and are printed by `checkparams` at the start of each build.
- **APR is NOT enabled by `SETUP=star`**: in the committed `Makefile_setups`, `APR=yes` (→ `-DAPR`) is set only by `SETUP=testapr`. To build the APR binary used for the binary-star runs, pass it explicitly: `make SYSTEM=gfortran SETUP=star APR=yes`. Check `build/.make_lastfppflags` after a build to confirm what was actually compiled (it currently shows `-DGRAVITY -DAPR`, i.e. the last build was `SETUP=star APR=yes`; a build that silently dropped APR shows the flags without `-DAPR`).
- Compile-time switches are `#ifdef` blocks in `src/main/config.F90` (module `dim`, e.g. `ISOTHERMAL`, `MAXPTMASS`, `APR`). Do NOT edit `build/config.F90` if it exists — the source of truth is `src/main/config.F90`; `build/` is just the object dir.
- Setup source files live in `src/setup/setup_*.f90`; a new setup must also get a `SETUP=` block with `KNOWN_SETUP=yes` in `build/Makefile_setups` or make will reject it. A few obsolete SETUPs (e.g. `mcfost`, `planets`, `binarydisc`, `warp`) are silently remapped to generic setups with a warning.

## Tests

- Build+run test suite: `make SETUP=test phantomtest && ./bin/phantomtest` (the `make test` target is the shortcut).
- Run a subset by passing an argument: `./bin/phantomtest derivs`, or `gravity`, `dust`, `gr`, `ptmass`, `apr`, `growth`, `nimhd`, `kdtree`, ... (valid names in `src/tests/testsuite.f90`).
- Tests are compiled conditionally by SETUP: e.g. `SETUP=testgrav` + `./bin/phantomtest gravity`; `SETUP=testgr` + `gr ptmass`; `SETUP=testdust` + `dust`; `SETUP=testapr` + `apr derivs`. Full mapping in `.github/workflows/test.yml`.
- With `SETUP=testapr`, only run subsets — the full suite (`./bin/phantomtest` with no args) exits with "APR not currently compatible with test suite". The `apr` test is the one that matters for merge work: `make SYSTEM=gfortran SETUP=testapr phantomtest && ./bin/phantomtest apr`. It checks angular momentum, linear momentum, total/kinetic/thermal energy, entropy and particle count across a split+merge cycle (tolerances ~1e-14; the 4->2 merge passes E_therm with exactly 0.0 error and E_kin with ~2e-16).
- Pre-existing failures on this branch (verified against pristine HEAD, do not chase them): the `derivs` test dies with "mtree + apr: totmass_node==0", and the `kdtree` test produces NaN (it allocates ~6.85 GB on this 7.6 GB machine) — it has also passed intermittently, treat as flaky. `neigh` passes.
- Switching SETUPs triggers `make clean`, so building `SETUP=testapr phantomtest` deletes `bin/phantom`; rebuild `SETUP=star APR=yes phantom` and re-copy the binary into run dirs afterwards. Also, `bin/phantom_version` (the "Pre-processor flags used" header) is only regenerated by the main-binary build and can be STALE after SETUP switches — verify what was compiled via `build/.make_lastfppflags`, not the header.
- The Fortran unit-test suite is `src/tests/`; standalone analysis tests are separate Python/Cython scripts in `scripts/` (e.g. `test_analysis_ce.py`).

## Run-directory workflow

- Simulations are NOT run from the repo root. Use a separate run directory (an untracked folder in the repo, e.g. the user's AGB-star test set `2ia-test-mini/`).
- `scripts/writemake.sh` writes a `Makefile` that calls repo make with `RUNDIR="${PWD}"` and copies binaries (`phantom`, `phantom_version`) into the run dir. Run it ONLY inside a run folder — never overwrite the `Makefile` in the repo root. `SETUP` is taken from the first argument (e.g. `~/phantom/scripts/writemake.sh star > Makefile`); without an argument no SETUP is written. Generated Makefiles hardcode `PHANTOMDIR` from whichever machine ran it — if a run dir's Makefile points at a path that doesn't exist here (e.g. the user's `/home/clmu/phantom`), regenerate it.
- `2ia-test-mini/` is the user's AGB-star test set (SETUP=star; renamed from `2ia-mini-test/`, which no longer exists). Each subdir is a code-variant comparison and holds three phantom jobs, one per `.in` file:
  - `star` = single-star runs (setup+relax from `star.setup`, then evolution); `lumo` = binary runs (2 sinks, the relaxed AGB star is one component); `fall` = binary runs with velocities reduced by `1/15.806274386` for a violent free-fall-like conservation test. `fall_00000.tmp` is generated from `lumo_00000` by `init-fall-from-lumo.py` (sarracen-based).
  - Subdirs: `merge12-com/` (12->6 merge, "com" = centre-of-mass variant), `merge2/` (2->1), `merge4/` (current 4->2, built from 6047fc117), `no-apr--np172032/` and `no-apr--np21504/` (APR-off controls at 172032 and 21504 = 172032/8 particles — the latter matches the APR coarsest mass), `t/` (scratch). Each subdir's `phantom_version` records its build: `merge*` dirs show `-DGRAVITY -DAPR`, no-apr dirs `-DGRAVITY` only. Don't assume the flags from one dir carry to another.
  - The `fall` runs are long and partially done (`.ev` last times: merge12-com t≈2.6e4, merge2 t≈2.8e4, merge4 t≈2.8e4, no-apr dirs t≈6e4 / 1e5); merge dirs keep only `fall_00000` plus `.ev` files, so don't expect full dump sets there.
  - Gotchas: `star.setup` in each subdir references `../AGB_th.data` (MESA profile), which lives at `2ia-test-mini/AGB_th.data` — so `phantomsetup` re-runs work; `star.dat` is the already-processed (softened) profile it produces. APR parameters are runtime options in the `.in` files (`apr_max=3`, `ref_dir=-1`, `apr_type=2` sink-centred, `apr_rad=104`, `apr_drad=60`).
- `merge4-test/` (repo root) is the previous scratch run dir (star-only, t=3000) — superseded by `2ia-test-mini/`. All run dirs are disposable; create your own for any new test work. Dumps are numbered from the next free number after the input `dumpfile`.
- Input files (`star.in`, etc.), output dumps and such run dirs are **never committed**; keep them untracked.
- `phantomsetup` writes an initial dump like `star_00000.tmp` — the `.tmp` suffix means the file is "incomplete" (some column not yet filled in, though all info to derive it is present). The complete `star_00000` appears once the main `phantom` binary runs (`write_initial_dump` in `src/main/initial.F90` strips the suffix and deletes the `.tmp`).
- Runtime data tables (EOS files etc.) are found relative to the `PHANTOM_DIR` env var (else `./`); the repo's `data/` dir must be reachable for runs. In a run dir: `export SYSTEM=gfortran PHANTOM_DIR=/home/coder/phantom; make APR=yes && ./phantom star > run.log 2>&1`.
- **Memory**: this machine has only 7.6 GB RAM (2 GB swap). APR multiplies `maxp` by 8 (`update_max_sizes` in `src/main/config.F90`), and reading a dump without `-maxp` first allocates the default `maxp_alloc = 5200000` (`src/main/config.F90`) — ~42 GB, OOM-killed. Always pass `-maxp` sized to the run (≥ `8*npart` with APR, ≥ `npart` without): the new test set's star has 172032 particles full-res, APR runs hold ~43k particles (`-maxp=400000` is plenty). The input file must come FIRST: `./phantom star -maxp=400000` (single or double dash both work). The reverse order (`./phantom -maxp=400000 star`) makes phantom try to open an input file named `-maxp=400000.in`.
- **Timing**: the `.in` files use `tmax = 2e5` with `dtmax = 50` (4000 dumps); at ~27 s per 100 time units on this 8-logical-core CPU a full run is ~15 h — the comparison dirs hold runs still in progress. For debugging, edit `tmax` (and `dtmax`, the dump interval) in the `.in` file down to ~300-600 units.
- The binary **rewrites the input `.in` file at the end of each run** (`dumpfile`/`logfile` are bumped to the next numbers), so restore `dumpfile = star_00000` (and `logfile`) before restarting from the original dump. When editing `.in` files programmatically, anchor the key name (e.g. `s/^ *tmax =/.../`) — an unanchored `s/tmax/` also matches `dtmax`. The `.ev` file name follows the `logfile` stem (star01.log → star01.ev), and its columns are labelled in the `#` header (time, ekin, etherm, emag, epot, etot, totmom, angtot, ...) — the last two are handy for quick p/L conservation checks.
- Run simulations in the foreground with a long tool timeout — backgrounded (`nohup ... &`) processes die when the shell session ends. For energy work, also capture the log: the periodic summary prints `split since last` / `merged since last` counts and the per-level particle distribution (npart change per summary = splits − nkilled/2, with nkilled = 2 per pair in the old 2->1 merge, 4 per group in the current 4->2).

## Data analysis with Python

- The `.venv` at the repo root has the packages for analysis — activate it (`source .venv/bin/activate`) or call `.venv/bin/python` directly. **`scripts/pyphantom` is Python 2 only** and will not import under this venv — don't use it.
- **`sarracen` reads dumps directly**: `from sarracen import sarracen; sdf, sdf_sink = sarracen.read_phantom("star_00000")` (returns pandas DataFrames). **Use the local source clone at `sarracen/` (untracked)** — the pip-installed copy has been removed from the venv, so `import sarracen` only works when the venv python runs with cwd inside `sarracen/` or with `PYTHONPATH=/home/coder/phantom/sarracen` (the local tree has the latest APR corrections, e.g. the `apr_level`→`mass` column handling in `sarracen/sarracen/readers/read_phantom.py`). DataFrames have per-particle `x,y,z,vx,vy,vz,u,h,poten,apr_level,mass,...` columns.
- Dump-file semantics that are easy to get wrong:
  - `poten(i)` is the **total** potential energy of particle i (the 0.5·m_i factor is already folded in, `force.F90` `epoti = 0.5*pmassi*(...)`). The `.ev` `epot` column is `Σ poten(i)` and is correct — do NOT re-weight by mass.
  - `mass` per particle = `massoftype(1)/2**(apr_level-1)` (APR). `apr_level` is stored in dumps and restored on restart; `init_apr` only rescales `massoftype` by `2**(apr_max-1)` when the dump has no levels.
  - `massoftype` and the header live in the tagged binary header; the arrays are Fortran sequential unformatted records (little-endian on this machine, real*8 by default), with each array written as a [16-char tag record][data record] pair and interleaved block-header records — a naive tag/data pairing will misalign.

## APR debugging notes (state of branch apr-flexbound9-relax-merge4)

- **Merging is 4 particles -> 2**, committed in `6047fc117` "(apr) merge 4->2" (HEAD; it reworked the earlier `6a9b1c1d2` — see git log if diffing against older notes). The 2->1 and 12->6 versions live in git history (`bfc2d9a9a` "merge 2->1", `ee9683dc6` "implemented 12-> 6 conservative particle merging"). E_kin, linear momentum and angular momentum are conserved EXACTLY by construction per group; the `apr` unit test passes on this HEAD (exact numbers in Tests).
- **Merge construction in `merge_with_special_tree` (`src/main/apr.f90`)**: work in the group's COM frame; the pair axis must lie in the plane ⊥ the group's angular momentum (2 free DOF: separation + in-plane orientation). For a pairing {a,b},{c,d}, the sum of squared child↔parent distances is D² = 4r² + Σ|p_i|² − 4r·|P(p_a+p_b)| (P = projection onto the plane ⊥ L), minimised at r = |P(p_a+p_b)|/2 — each child sits at the projection of its own pair's centroid onto that plane. The best of the 3 pairings is the one with the longest projected pair-sum: `vec = svec_best/|svec_best|`, `r_sep = max(0.5*|svec_best|, sqrt(rl2))` with `rl2 = am2/(8*ekin)` the feasibility floor that keeps v_tangential = sqrt(am2)/(4*r_sep) real. If the projected pair-sum ≈ 0 (all 4 parents lumped together in that plane) it `warning`s and sets r_sep = 0 (children at the COM).
- **Velocities and inheritance**: vperp (tangential) from L, vpar = sqrt(max(0, 0.5*ekin − vperp²)) from E_kin with sign = the group's mean radial motion `sv`; u averaged (thermal conserved), h rescaled by 2^(1/3). Each child inherits from its 2 **actual closest** parents — squared distances to the child position sorted with `indexx` (module `sortutils`; **file `utils_sort.f90`**, module name ≠ file name) — so `combine_two_particles` gets the closest pairs, not fixed 1-3/2-4. The old `eigen_symmetric3` covariance-eigenvector fallback is gone (dropped in the 6047fc117 rework).
- **Merge selection: leaf bounding-box centre crossed** (`get_cell_location` in the serial `over_cells_part1` loop) — plus a per-particle check: the leaf's level is the MAX of the COM's level and each member's own level (`apri_at_cells_com`), so a group merges only once all 4 particles have crossed the boundary (this per-particle check was introduced by the 6047fc117 rework itself; the older "merge only if ALL particles crossed" commit `bb2b6d5aa` lives only on the `mergeoneside` branch). On top of that, a straddle check in the merge loop skips the merge unless BOTH new particles are fully inside the coarser region (`get_apr(pos_com ± r_sep*vec) < current_apr`). The straddle check is essential: without it, half-crossed boundary groups are merged and then re-split the next step. Measured on the OLD star-only test: ~95% churn (~500-800 merges + ~220 splits per 50 units), |p| drift 1.9e-4, and the sink gets kicked (diagnose via the sink `.ev`: `starSink0001N01.ev` single-star, `fallSink0001N01.ev`/`fallSink0002N01.ev` binary runs — |r|,|v| growing). With the check: ~0-56 merges per 50 units, |p| ~ 7e-6, no sink kick.
- **Tree grouping: 4 particles per leaf.** The merge tree is built with `for_apr=.true.`; `src/main/kdtree.F90` `construct_node` splits while `npnode > 4`, and `special_sort_particles_in_cell` (`nchild_in = 4`) forces every leaf to exactly 4 particles: it partitions by the pivot, then slides particles across the boundary (nearest to the pivot first, via `dpivot`) so both children end up with sizes divisible by 4 (with direction overrides when one child has < 4 particles; an `error` is raised if the incoming count is not divisible — the message still says "divisible by 2", a leftover). `merge_with_special_tree` truncates `nmerge` to a multiple of 4, and `update_apr` calls it when `nmerge >= 4` (the old `> 11` threshold was a 12->6 leftover).
- **Crash-on-unexpected is the house style** (explicit user requirement): the merge code `fatal`s on `n_cell /= 4` and on a non-finite pair configuration (`isnan` check) rather than silently skipping. Keep it that way; do not convert these to silent `cycle`s.
- **Potential energy is still NOT conserved by merges** (user: ignore for now): children at the pair centroids vs the old 4 particles change Epot per group. Measured on the OLD star-only test: -1.2e-5 over 3000 units in `merge4-test` (rel 7.4e-3, ~4e-9 per unit — comparable to the 2->1 era per unit time). A future fix would subtract ΔE_pot from `vxyzu(4)` of both new particles.
- **`vxyzu_merge(4,:)` (u) must be copied in `update_apr`** (`if (maxvxyzu > 3) vxyzu_merge(4,mm) = vxyzu(4,ii)`) — without it the merged particles silently get u = 0 and the thermal energy is lost (bug found and fixed this session).
- Three smaller bugs found in the same audit were fixed by the user (commits `0dcc2e69a` "(apr) parallelization bug fix" and `f4d3ff77d` "(apr) bug fix") and are now in this branch: (1) the merge used `aprmassoftype(igas, apr_level(...))` indexed with the special tree's `xyzh_merge` indices (1..nmerge) instead of real particle indices — moot in the 4->2 code since all group members share one mass, but beware if reintroducing per-particle masses; (2) `combine_two_particles` now does `treecache(5,keep) = treecache(5,keep)*2` instead of `- int(1,kind=1)`, which had set the tree-cache mass to ≈ -1 (`src/main/part.F90:1444`). None of the three affected the measured energy drift.
- **Loop structure in `update_apr` (post-6047fc117)**: the split loop is deliberately serial (code comment: "should *probably* not be parallelised"); the merge-candidate loop is `!$omp parallel do default(none)` with `reduction(+:nmerge)` / `reduction(+:npart_regions)` and explicit `shared`/`private` lists; the prefix-scan loop building `scan_array` must stay serial (commented as such) — don't parallelise it.
- Still-open latent issues (verified by reading, all currently benign): `adjust_entropy` (utils_apr.f90) is entirely commented out; `integrate_geodesic` (split_dir=2 / GR) has a dt-shrinking loop that can hang when `iexternalforce=0`; `ref_dir=-1` maps the **innermost** region to level 1 = the **largest** particle mass (coarsest, `aprmassoftype(:,i) = massoftype/(2**(i-1))` in `init_apr`) — the centre of the star gets derefined, and merges happen at the inner boundary where |ΔE| ∝ 1/r³ is largest. The APR unit test uses `ref_dir=1` (centre finest), but the `2ia-test-mini` runs use `ref_dir=-1` — re-check the region↔level↔mass mapping before assuming the configuration does what it seems to.
- `poten` bookkeeping at events (halved on split, summed on merge) is consistent and transient — `poten` is recomputed from scratch in every force call, so diagnostics should ignore the stored values between dumps.
- Instrumentation gotchas: any new local used inside the merge loop's OpenMP region must be added to the `!$omp private(...)` lists or the build fails (module vars used in the region — e.g. `get_apr`, `icentre` — must go in `shared(...)`); keep lines ≤132 chars and declare all variables (gfortran `-Wall`/`-std=f2008` flag truncation and `implicit type`; `-Werror` only with `NOWARN=yes`, which the current build flags in `build/.make_lastfflags` do not have); after editing `apr.f90` rebuild with `make SYSTEM=gfortran SETUP=star APR=yes` (full rebuild on config change is normal). To see merge diagnostics (`nmerge particles selected for merge`, `merged: nkilled kk`, per-level `npart_regions`) flip `apr_verbose = .true.` at the top of `src/main/apr.f90` — also the fastest way to tell whether the merge tree is being built/grouped as expected.
