# AGENTS.md

Phantom: 3D SPH/MHD astrophysics code, written in Fortran 90 (`gfortran`/`ifort`/`ifx`/`aocc`). The whole codebase is Fortran; Python exists only for analysis scripts (`scripts/pyphantom`, docs build).

## Build

- The root `Makefile` is a thin wrapper that delegates everything to `build/Makefile` (`cd build; make ...`). Run make from the repo root.
- Both `SYSTEM` and `SETUP` are **required** on the command line, e.g.:
  `make SYSTEM=gfortran SETUP=star`
  - `SYSTEM` selects a compiler block in `build/Makefile_systems`; this machine always uses `gfortran` (flags in `build/Makefile_defaults_gfortran`).
  - `SETUP` selects a compile-time configuration block in `build/Makefile_setups` (e.g. `star`, `disc`, `sedov`, `test`, `testgrav`, ...). Unknown SETUP = hard error with a hint. Day-to-day work uses `SETUP=star` (sometimes `dustystar` or `radstar`) for binary-star simulations.
- Default target `make` builds the main `phantom` binary. Other binaries, each its own target (all need SETUP): `phantomsetup`, `phantomtest`, `phantommoddump` (alias `moddump`), `phantomanalysis` (alias `analysis`), `phantomevcompare`, ...
- Changing SETUP/SYSTEM/FFLAGS/FPPFLAGS automatically triggers `make clean` (tracked via `build/.make_last*` files). Full rebuilds on config change are normal, not a bug.
- Binaries land in `bin/` (gitignored via `bin/.gitignore` containing `*`); `build/*.o` and `*.mod` are gitignored, as is `build/phantom-version.h` (generated from version numbers at the top of `build/Makefile`).
- `OPENMP=yes` (OpenMP) and `DOUBLEPRECISION=yes` are defaults; `DEBUG=yes` adds debug flags. Extra switches via env var, e.g. `MPI=yes` (or `MPI=openmpi`).

### Config system (important)

- `.F90` sources are C-preprocessed (cpp); `.f90` are not. Preprocessor macros (`-DGRAVITY`, `-DMHD`, ...) come from the SETUP block in `build/Makefile_setups` and are printed by `checkparams` at the start of each build.
- **APR is NOT enabled by `SETUP=star`**: in the committed `Makefile_setups`, `APR=yes` (→ `-DAPR`) is set only by `SETUP=testapr`. To build the APR binary used for the binary-star runs, pass it explicitly: `make SYSTEM=gfortran SETUP=star APR=yes`. Check `build/.make_lastfppflags` after a build to confirm what was actually compiled (it currently shows `-DGRAVITY -DAPR`, i.e. the last build was `SETUP=star APR=yes`; a build that silently dropped APR shows the flags without `-DAPR`).
- Compile-time switches are `#ifdef` blocks in `src/main/config.F90` (module `dim`, e.g. `ISOTHERMAL`, `MAXPTMASS`, `APR`). Do NOT edit `build/config.F90` if it exists — the source of truth is `src/main/config.F90`; `build/` is just the object dir.
- Setup source files live in `src/setup/setup_*.f90`; a new setup must also get a `SETUP=` block with `KNOWN_SETUP=yes` in `build/Makefile_setups` or make will reject it. A few obsolete SETUPs (e.g. `mcfost`, `planets`, `binarydisc`, `warp`) are silently remapped to generic setups with a warning.

## Tests

- Build+run test suite: `make SETUP=test phantomtest && ./bin/phantomtest` (the `make test` target is the shortcut).
- Run a subset by passing an argument: `./bin/phantomtest derivs`, or `gravity`, `dust`, `gr`, `ptmass`, `apr`, `growth`, `nimhd`, `kdtree`, ... (valid names in `src/tests/testsuite.f90`).
- Tests are compiled conditionally by SETUP: e.g. `SETUP=testgrav` + `./bin/phantomtest gravity`; `SETUP=testgr` + `gr ptmass`; `SETUP=testdust` + `dust`; `SETUP=testapr` + `apr derivs`. Full mapping in `.github/workflows/test.yml`.
- With `SETUP=testapr`, only run subsets — the full suite (`./bin/phantomtest` with no args) exits with "APR not currently compatible with test suite". The `apr` test is the one that matters for merge work: `make SYSTEM=gfortran SETUP=testapr phantomtest && ./bin/phantomtest apr`. It checks angular momentum, linear momentum, total/kinetic/thermal energy, entropy and particle count across a split+merge cycle (tolerances ~1e-14; the 4->2 merge passes E_kin/E_therm checks with exactly 0.0 error).
- Pre-existing failures on this branch (verified against pristine HEAD, do not chase them): the `derivs` test dies with "mtree + apr: totmass_node==0", and the `kdtree` test produces NaN (it allocates ~6.85 GB on this 7.6 GB machine) — it has also passed intermittently, treat as flaky. `neigh` passes.
- Switching SETUPs triggers `make clean`, so building `SETUP=testapr phantomtest` deletes `bin/phantom`; rebuild `SETUP=star APR=yes phantom` and re-copy the binary into run dirs afterwards. Also, `bin/phantom_version` (the "Pre-processor flags used" header) is only regenerated by the main-binary build and can be STALE after SETUP switches — verify what was compiled via `build/.make_lastfppflags`, not the header.
- The Fortran unit-test suite is `src/tests/`; standalone analysis tests are separate Python/Cython scripts in `scripts/` (e.g. `test_analysis_ce.py`).

## Run-directory workflow

- Simulations are NOT run from the repo root. Use a separate run directory (an untracked folder in the repo, e.g. the user's AGB-star test case `2ia-mini-test/`).
- `scripts/writemake.sh` writes a `Makefile` that calls repo make with `RUNDIR="${PWD}"` and copies binaries (`phantom`, `phantom_version`) into the run dir.
- `2ia-mini-test/` is an AGB-star test case (SETUP=star): it holds the user's comparison runs as subdirs — `merge12/` (12->6-era merge, dumps to t=20000, no merging during the star's initial ~1000-unit contraction), `merge4/` (4->2-era merge, dumps to t=15000, worse energy conservation — the pre-fix reference), `nosplitmerge/` (APR splitting/merging disabled — energy-conservation control, `split since last: 0` / `merged since last: 0` in its log). `merge4-test/` is the current scratch run dir (3000-unit run, 60 dumps `star_00001..00060` at `dtmax=50`; note dumps are numbered from the next free number after the input `dumpfile`). All run dirs are disposable — create your own (`writemake.sh star > Makefile` inside it) for any new test work.
- Run `scripts/writemake.sh` ONLY inside a run folder — never overwrite the `Makefile` in the repo root. `SETUP` is taken from the first argument (e.g. `~/phantom/scripts/writemake.sh star > Makefile`); without an argument no SETUP is written.
- Input files (`star.in`, etc.), output dumps and such run dirs are **never committed**; keep them untracked.
- `phantomsetup` writes an initial dump like `star_00000.tmp` — the `.tmp` suffix means the file is "incomplete" (some column not yet filled in, though all info to derive it is present). The complete `star_00000` appears once the main `phantom` binary runs (`write_initial_dump` in `src/main/initial.F90` strips the suffix and deletes the `.tmp`).
- Runtime data tables (EOS files etc.) are found relative to the `PHANTOM_DIR` env var (else `./`); the repo's `data/` dir must be reachable for runs. In a run dir: `export SYSTEM=gfortran PHANTOM_DIR=/home/coder/phantom; make APR=yes && ./phantom star > run.log 2>&1`.
- **Memory**: this machine has only 7.6 GB RAM (2 GB swap). APR multiplies the allocation by 8 (`update_max_sizes` in `src/main/config.F90`), and the default `maxp_alloc = 5200000` (`src/main/config.F90`) needs ~42 GB and gets OOM-killed. Always run with `-maxp=100000`, with the input file FIRST: `./phantom star -maxp=100000` (single or double dash both work). The reverse order (`./phantom -maxp=100000 star`) makes phantom try to open an input file named `-maxp=100000.in`.
- **Timing**: the full 20000-unit run (400 dumps at `dtmax = 50`) takes ~1.5 h on this machine (8-logical-core CPU, ~27 s per 100 time units). For debugging, edit `tmax` (and `dtmax`, the dump interval) in `star.in` down to ~300-600 units.
- The binary **rewrites `star.in` at the end of each run** (`dumpfile`/`logfile` are bumped to the next numbers), so restore `dumpfile = star_00000` (and `logfile`) before restarting from the original dump. When editing `star.in` programmatically, anchor the key name (e.g. `s/^ *tmax =/.../`) — an unanchored `s/tmax/` also matches `dtmax`. The `.ev` file name follows the `logfile` stem (star01.log → star01.ev), and its columns are labelled in the `#` header (time, ekin, etherm, emag, epot, etot, totmom, angtot, ...) — the last two are handy for quick p/L conservation checks.
- Run simulations in the foreground with a long tool timeout — backgrounded (`nohup ... &`) processes die when the shell session ends. For energy work, also capture the log: the periodic summary prints `split since last` / `merged since last` counts and the per-level particle distribution (npart change per summary = splits − merges/2, because `nkilled` counts the killed children: 2 per pair in the old 2->1 merge, 4 per group in the current 4->2).

## Data analysis with Python

- The `.venv` at the repo root has the packages for analysis — activate it (`source .venv/bin/activate`) or call `.venv/bin/python` directly. **`scripts/pyphantom` is Python 2 only** and will not import under this venv — don't use it.
- **`sarracen` reads dumps directly**: `from sarracen import sarracen; sdf, sdf_sink = sarracen.read_phantom("star_00000")` (returns pandas DataFrames). **Use the local source clone at `sarracen/` (untracked)** — the pip-installed copy has been removed from the venv, so `import sarracen` only works when the venv python runs with cwd inside `sarracen/` or with `PYTHONPATH=/home/coder/phantom/sarracen` (the local tree has the latest APR corrections, e.g. the `apr_level`→`mass` column handling in `sarracen/sarracen/readers/read_phantom.py`). DataFrames have per-particle `x,y,z,vx,vy,vz,u,h,poten,apr_level,mass,...` columns.
- Dump-file semantics that are easy to get wrong:
  - `poten(i)` is the **total** potential energy of particle i (the 0.5·m_i factor is already folded in, `force.F90` `epoti = 0.5*pmassi*(...)`). The `.ev` `epot` column is `Σ poten(i)` and is correct — do NOT re-weight by mass.
  - `mass` per particle = `massoftype(1)/2**(apr_level-1)` (APR). `apr_level` is stored in dumps and restored on restart; `init_apr` only rescales `massoftype` by `2**(apr_max-1)` when the dump has no levels.
  - `massoftype` and the header live in the tagged binary header; the arrays are Fortran sequential unformatted records (little-endian on this machine, real*8 by default), with each array written as a [16-char tag record][data record] pair and interleaved block-header records — a naive tag/data pairing will misalign.

## APR debugging notes (state of branch apr-flexbound9-relax-merge4)

- **Merging is 4 particles -> 2**, committed in `6a9b1c1d2` "(apr) merge 4->2" (the 2->1 and 12->6 versions are in git history: `bfc2d9a9a` "merge 2->1" and its parent). Total E_kin, linear momentum and angular momentum are conserved EXACTLY by construction per group; the `apr` unit test (`SETUP=testapr` + `./bin/phantomtest apr`) verifies E_kin/E_therm with exactly 0.0 error.
- **The construction in `merge_with_special_tree` (`src/main/apr.f90`)**: work in the group's COM frame; the pair axis must lie in the plane ⊥ the group's angular momentum (2 free DOF: separation + in-plane orientation). `r_sep` and the axis MINIMISE the sum of squared distances between each child and its 2 parents: for a pairing {a,b},{c,d}, D² = 4r² + Σ|p_i|² − 4r·|P(p_a+p_b)| (P = projection onto the plane ⊥ L), minimised at r = |P(p_a+p_b)|/2 — each child sits at the projection of its own pair's centroid onto that plane. The best pairing is the one with the longest projected pair-sum (all 3 pairings tried). The covariance-eigenvector axis (`eigen_symmetric3`, a Jacobi 3x3 solver in apr.f90) is only the degenerate fallback (projected pair-sum ≈ 0, where the axial second moment λ/4 is matched instead). r is clamped from below by the angular-momentum feasibility floor `rl2 = am2/(8*ekin)` so v_tangential = sqrt(am2)/(4r) stays real. Velocities: v_tangential from L, v_radial from E_kin (sign = the group's mean radial motion); u averaged (thermal conserved), h rescaled by 2^(1/3). Each child inherits from its 2 **actual closest** parents — distances to the child position sorted with `indexx` from module `sortutils` (**file `utils_sort.f90` but the module is named `sortutils`**) — i.e. `combine_two_particles` gets the closest pairs, not fixed 1-3/2-4.
- **Merge selection: leaf bounding-box centre crossed** (`get_cell_location` in the serial `over_cells_part1` loop) — PLUS a straddle check: the merge is skipped unless BOTH new particles are fully inside the coarser region (`get_apr(pos_com ± r_sep*vec) < current_apr`). The straddle check is essential: without it the centre-crossed criterion merges half-crossed boundary groups whose children straddle the boundary and are re-split the next step — measured ~95% churn (~500-800 merges + ~220 splits per 50 units), |p| drift 1.9e-4, and the sink gets kicked (diagnose via `starSink0001N01.ev`: |r|,|v| growing). With the check: ~0-56 merges per 50 units, |p| ~ 7e-6, no sink kick. Git history fact: the "merge only if ALL particles crossed" commit `bb2b6d5aa` lives on the `mergeoneside` branch, NOT in this lineage (12->6 at `bfc2d9a9a~1` used the cell CoM only); a per-particle all-crossed criterion gives ZERO merges in the star test (nearest-4 groups straddle the boundary).
- **Tree grouping: 4 particles per leaf.** The merge tree is built with `for_apr=.true.`; `src/main/kdtree.F90` `construct_node` splits while `npnode > 4`, and `special_sort_particles_in_cell` (`nchild_in = 4`) forces every leaf to exactly 4 particles. Two robustness fixes were needed: the all-on-one-side fallback split keeps sizes divisible by 4 (`nl = 4*(npnode/8)` for `apr_tree`), and non-divisible cells degrade to a plain bisection instead of an error. `merge_with_special_tree` truncates `nmerge` to a multiple of 4, and `update_apr` calls it when `nmerge >= 4` (the old `> 11` threshold was a 12->6 leftover).
- **Crash-on-unexpected is the house style** (explicit user requirement): the merge code `fatal`s on `n_cell /= 4` and on a non-finite pair configuration (`isnan` check) rather than silently skipping. Keep it that way; do not convert these to silent `cycle`s.
- **Potential energy is still NOT conserved by merges** (user: ignore for now): children at the pair centroids vs the old 4 particles change Epot per group; measured -1.2e-5 over 3000 units in `merge4-test` (rel 7.4e-3, ~4e-9 per unit — comparable to the 2->1 era per unit time). A future fix would subtract ΔE_pot from `vxyzu(4)` of both new particles.
- **`vxyzu_merge(4,:)` (u) must be copied in `update_apr`** (`if (maxvxyzu > 3) vxyzu_merge(4,mm) = vxyzu(4,ii)`) — without it the merged particles silently get u = 0 and the thermal energy is lost (bug found and fixed this session).
- Three smaller bugs found in the same audit were fixed by the user (commits `0dcc2e69a` "(apr) parallelization bug fix" and `f4d3ff77d` "(apr) bug fix") and are now in this branch: (1) the merge used `aprmassoftype(igas, apr_level(...))` indexed with the special tree's `xyzh_merge` indices (1..nmerge) instead of real particle indices — moot in the 4->2 code since all group members share one mass, but beware if reintroducing per-particle masses; (2) `combine_two_particles` now does `treecache(5,keep) = treecache(5,keep)*2` instead of `- int(1,kind=1)`, which had set the tree-cache mass to ≈ -1 (`src/main/part.F90:1444`); (3) the merge loop's `relaxlist` update uses `!$omp critical` instead of `atomic capture` to avoid a read/write race with the follow-up scan. None of the three affected the measured energy drift.
- Still-open latent issues (verified by reading, all currently benign): `adjust_entropy` (utils_apr.f90) is entirely commented out; `integrate_geodesic` (split_dir=2 / GR) has a dt-shrinking loop that can hang when `iexternalforce=0`; `ref_dir=-1` maps the **innermost** region to level 1 = the **largest** particle mass (coarsest) — the centre of the star gets derefined, and merges happen at the inner boundary where |ΔE| ∝ 1/r³ is largest (the APR test suite uses `ref_dir=1`, centre finest; re-check the region↔level↔mass mapping before assuming the configuration does what it seems to).
- `poten` bookkeeping at events (halved on split, summed on merge) is consistent and transient — `poten` is recomputed from scratch in every force call, so diagnostics should ignore the stored values between dumps.
- Instrumentation gotchas: any new local used inside the merge loop's OpenMP region must be added to the `!$omp private(...)` lists or the build fails (module vars used in the region — e.g. `get_apr`, `icentre` — must go in `shared(...)`); keep lines ≤132 chars and declare all variables (gfortran `-Wall`/`-std=f2008` flag truncation and `implicit type`; `-Werror` only with `NOWARN=yes`, which the current build flags in `build/.make_lastfflags` do not have); after editing `apr.f90` rebuild with `make SYSTEM=gfortran SETUP=star APR=yes` (full rebuild on config change is normal). To see merge diagnostics (`nmerge particles selected for merge`, `merged: nkilled kk`, per-level `npart_regions`) flip `apr_verbose = .true.` at the top of `src/main/apr.f90` — also the fastest way to tell whether the merge tree is being built/grouped as expected.
